# 面向长时间运行应用开发的 Harness 设计

## 为什么简单实现远远不够

我们此前已经证明，harness 设计对长时间运行的代理编码效果有重大影响。在早期的[实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)中，我们使用了一个初始化代理将产品规格拆解为任务列表，然后由编码代理逐一实现各个功能，最后通过交接工件在会话间传递上下文。更广泛的开发者社区也得出了类似的洞见，例如 "[Ralph Wiggum](https://ghuntley.com/ralph/)" 方法就利用 hooks 或脚本让代理持续处于迭代循环中。

但一些问题始终存在。面对更复杂的任务，代理仍然容易随时间推移逐渐偏离正轨。在分析这一问题时，我们观察到代理在执行此类任务时存在两种常见的失败模式。

第一种是，当上下文窗口逐渐填满时，模型容易在漫长的任务中丧失连贯性（参见我们关于[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)的文章）。某些模型还会表现出"上下文焦虑"——当它们认为自己接近上下文限制时，会过早地开始收尾工作。上下文重置——即完全清空上下文窗口并启动一个新的代理，同时通过结构化交接传递前一个代理的状态和后续步骤——可以同时解决这两个问题。

这与压缩（compaction）不同。压缩是在原地总结对话的早期部分，让同一个代理基于缩短后的历史继续工作。虽然压缩保持了连续性，但它没有给代理一个全新的起点，因此上下文焦虑仍然可能持续存在。重置则提供了一个全新的起点，代价是交接工件必须包含足够的状态信息，让下一个代理能够无缝接续工作。在我们早期的测试中，Claude Sonnet 4.5 表现出强烈的上下文焦虑，仅靠压缩无法支撑高质量的长任务执行，因此上下文重置成为 harness 设计中的关键组成部分。这解决了核心问题，但也给每次 harness 运行增加了编排复杂度、token 开销和延迟。

第二个问题是我们此前未曾讨论过的：自我评估。当被要求评估自己产出的工作时，代理往往会自信地对工作大加赞赏——即使从人类的角度看，质量明显只是差强人意。这个问题在设计等主观任务上尤为突出，因为不存在类似可验证软件测试的二值化检查。一个布局是精致还是平庸，这是一个判断问题，而代理在给自己的作品打分时几乎总是偏向正面。

然而，即使在具有可验证结果的任务上，代理有时仍会表现出糟糕的判断力，从而影响任务完成效果。将执行工作的代理与评审工作的代理分离开来，是解决这一问题的有效手段。这种分离并不能立即消除宽容倾向；评估者仍然是一个 LLM，天然倾向于对 LLM 生成的输出更为宽容。但调优一个独立的评估者使其保持怀疑态度，远比让生成器对自身作品吹毛求疵来得可行。而一旦有了外部反馈，生成器就有了具体的改进方向来迭代优化。

## 前端设计：让主观质量变得可评分

我首先在前端设计领域进行实验，因为自我评估问题在这里最为明显。在没有任何干预的情况下，Claude 通常会倾向于安全、可预测的布局方案——技术上功能完备，但视觉上平平无奇。

两个洞见塑造了我为前端设计构建的 harness。第一，虽然美感无法完全简化为一个分数——个人品味也始终存在差异——但通过编码设计原则和偏好的评分标准，确实可以改善结果。"这个设计好看吗？"很难一致地回答，但"它是否遵循了我们的优秀设计原则？"则为 Claude 提供了具体的评分依据。第二，通过将前端生成与前端评审分离，我们可以创建一个反馈循环，驱动生成器产出更高质量的输出。

基于这些考虑，我编写了四条评分标准，并在生成器和评估器代理的提示词中都提供了它们：

*   **设计质量：** 设计是否感觉是一个统一的整体，而非各个部分的拼凑？优秀的作品意味着颜色、排版、布局、图像和其他细节共同营造出独特的氛围和个性。
*   **原创性：** 是否有自主设计决策的痕迹，还是模板布局、库默认值和 AI 生成模式的堆砌？一位人类设计师应该能辨认出深思熟虑的创意选择。未修改的现成组件——或 AI 生成的典型痕迹，如白色卡片上的紫色渐变——在这里是不合格的。
*   **工艺：** 技术执行水平：排版层级、间距一致性、色彩和谐度、对比度。这是能力检查而非创意检查。大多数合理的实现在这方面默认表现不错；如果在这里失分，说明基本功有问题。
*   **功能性：** 独立于美学的可用性。用户能否理解界面的用途，找到主要操作入口，并在无需猜测的情况下完成任务？

我将设计质量和原创性的权重置于工艺和功能性之上。Claude 在工艺和功能性方面本就表现良好，因为所需的技术能力对模型来说往往是自然而然的。但在设计和原创性方面，Claude 的输出充其量只是乏善可陈。评分标准明确惩罚了高度通用的"AI 模板化"模式，并通过加重设计和原创性的权重，推动模型在审美上更大胆地尝试。

我使用带有详细分数分解的少样本示例来校准评估器。这确保了评估器的判断与我的偏好一致，并减少了跨迭代的分数漂移。

我在 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 上构建了这个循环，这使得编排工作变得直接明了。生成器代理首先根据用户提示词创建一个 HTML/CSS/JS 前端。我为评估器提供了 Playwright MCP，让它能在评分之前直接与实时页面交互，逐条评估每个标准并撰写详细评审。实际操作中，评估器会自行导航页面，截图并仔细研究实现效果后再给出评估。这些反馈随后回流到生成器，作为下一轮迭代的输入。每次生成都运行 5 到 15 轮迭代，每轮迭代通常会推动生成器朝更具特色的方向前进，因为它需要回应评估器的批评。由于评估器是主动导航页面而非对静态截图打分，每个周期都需要真实的运行时间。完整的运行可长达四个小时。我还指示生成器在每次评估后做出战略性决策：如果分数趋势向好，就精炼当前方向；如果当前方案不奏效，就转向一个完全不同的审美风格。

在各轮运行中，评估器的评分随迭代逐步提高后趋于平稳，仍有提升空间。有些生成过程是渐进式优化，另一些则在迭代之间出现了戏剧性的审美转向。

评分标准的措辞以我未完全预料到的方式引导了生成器。诸如"最好的设计应达到博物馆品质"这样的表述将设计推向了特定的视觉收敛方向，表明与评分标准关联的提示词直接塑造了输出的特征。

虽然分数总体上随迭代提高，但这一模式并不总是线性清晰的。后期的实现在整体上往往更好，但我经常发现某些中间迭代比最终迭代更合我意。实现复杂度也倾向于逐轮增加，生成器在回应评估器反馈时会尝试更宏大的方案。即使在第一轮迭代中，输出也比完全没有评分标准引导的基线明显更好，这表明评分标准及其相关表述本身就引导模型远离了通用的默认模式，而评估器反馈则在此基础上进一步推动优化。

在一个引人注目的案例中，我提示模型为一家荷兰艺术博物馆创建网站。到第九轮迭代时，它产出了一个虚构博物馆的简洁、深色主题落地页。页面视觉上很精致，但基本符合我的预期。然后在第十轮，它完全放弃了原有方案，将网站重新构想为一种空间体验：一个用 CSS 透视渲染的带格子地板的 3D 房间，艺术品以自由形式挂在墙上，通过门洞在展厅之间导航，而非滚动或点击。这是我此前从未在单次生成中见过的创造性飞跃。

## 扩展到全栈编码

基于这些发现，我将这种受 GAN 启发的模式应用到全栈开发中。生成器-评估器循环天然映射到软件开发生命周期，其中代码审查和 QA 扮演着与设计评估器相同的结构性角色。

### 架构

在我们早期的[长时间运行 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 中，我们通过一个初始化代理、一个逐功能实现的编码代理以及会话间的上下文重置来实现连贯的多会话编码。上下文重置是一个关键突破：该 harness 使用 Sonnet 4.5，而该模型表现出前述的"上下文焦虑"倾向。创建一个在上下文重置间也能良好工作的 harness，是保持模型专注于任务的关键。Opus 4.5 在很大程度上自行消除了这一行为，因此我得以从本 harness 中完全移除上下文重置。各代理作为一个连续会话贯穿整个构建过程，由 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 的自动压缩机制处理上下文增长。

在这项工作中，我在原始 harness 的基础上构建了一个三代理系统，每个代理解决我在先前运行中观察到的特定缺陷。系统包含以下代理角色：

**规划器（Planner）：** 我们之前的长时间运行 harness 要求用户预先提供详细的规格说明。我希望自动化这一步骤，因此创建了一个规划器代理，接收 1-4 句简单的提示词并将其扩展为完整的产品规格。我提示它在范围上保持雄心，聚焦于产品上下文和高层技术设计，而非详细的技术实现。这一强调是因为担心如果规划器试图预先指定粒度过细的技术细节并出了差错，规格中的错误就会级联影响下游实现。约束代理关注要交付的产出物，让它们在执行过程中自行探索路径，看起来更为明智。我还要求规划器寻找将 AI 功能融入产品规格的机会。（参见底部附录中的示例。）

**生成器（Generator）：** 早期 harness 中逐功能实现的方式在范围管理方面效果良好。我在此采用了类似模式，指示生成器以冲刺方式工作，从规格中每次选取一个功能。每个冲刺使用 React、Vite、FastAPI 和 SQLite（后改为 PostgreSQL）技术栈实现应用，生成器在每个冲刺结束时进行自我评估，然后交接给 QA。它还使用 git 进行版本控制。

**评估器（Evaluator）：** 早期 harness 产出的应用往往看起来令人印象深刻，但实际使用时仍有真实存在的 bug。为了捕获这些问题，评估器使用 Playwright MCP 像用户一样点击操作运行中的应用，测试 UI 功能、API 端点和数据库状态。然后根据发现的 bug 以及一组从前端实验移植而来的评分标准对每个冲刺进行评分——此处调整为涵盖产品深度、功能性、视觉设计和代码质量。每条标准设有硬性阈值，如果任何一条低于阈值，该冲刺即判定为失败，生成器将收到关于问题所在的详细反馈。

在每个冲刺开始前，生成器和评估器会协商一个冲刺合同：在任何代码编写之前就这一阶段"完成"的定义达成共识。这一步骤的存在是因为产品规格有意保持高层级，我需要一个环节来弥合用户故事与可测试实现之间的差距。生成器提出它要构建的内容以及如何验证成功，评估器审查该提案以确保生成器确实在构建正确的东西。双方迭代直至达成一致。

通信通过文件处理：一个代理写入文件，另一个代理读取后在该文件内或通过新文件作出回应，前者再读取新文件。生成器随后根据商定的合同进行构建，然后将工作交接给 QA。这确保了工作忠实于规格，同时避免过早过度指定实现细节。

### 运行 Harness

对于这个 harness 的第一个版本，我使用 Claude Opus 4.5，将用户提示词同时提交给完整 harness 和单代理系统进行对比。我使用 Opus 4.5，因为这是我开始这些实验时最好的编码模型。

我编写了以下提示词来生成一个复古视频游戏制作器：

> _创建一个 2D 复古游戏制作器，包含关卡编辑器、精灵编辑器、实体行为和可玩的测试模式等功能。_

下表展示了 harness 类型、运行时长和总成本。

| **Harness** | **时长** | **成本** |
| --- | --- | --- |
| 单代理 | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

Harness 的成本高出 20 倍以上，但输出质量的差异一目了然。

我期望的是一个能够构建关卡及其组成部分（精灵、实体、瓦片布局），然后点击播放即可实际游玩关卡的界面。我首先打开了单代理运行的输出，初始应用看起来符合这些预期。

然而，随着我深入点击，问题开始浮现。布局浪费了大量空间，固定高度的面板让大部分视口空空如也。工作流很僵硬。尝试填充关卡时，系统提示我先创建精灵和实体，但 UI 中没有任何东西引导我按这个顺序操作。更要紧的是，实际游戏是坏的。我的实体出现在屏幕上，但没有任何响应输入。查看代码后发现，实体定义与游戏运行时之间的连接是断开的，而且从表面上看不出断在哪里。

评估完单代理运行后，我将注意力转向 harness 运行。这次运行从相同的一句话提示词出发，但规划器步骤将提示词扩展为涵盖十个冲刺的 16 项功能规格。它远远超出了单代理运行所尝试的范围。除了核心编辑器和播放模式外，规格还要求包含精灵动画系统、行为模板、音效和音乐、AI 辅助精灵生成器和关卡设计器，以及带分享链接的游戏导出功能。我为规划器提供了我们的[前端设计技能](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)，它读取并使用该技能为应用创建了视觉设计语言，作为规格的一部分。对于每个冲刺，生成器和评估器协商一个合同，定义冲刺的具体实现细节以及用于验证完成度的可测试行为。

应用立即展现出比单代理运行更多的精致感和流畅度。画布使用了全部视口，面板尺寸合理，界面具有一致的视觉标识，与规格中的设计方向保持一致。单代理运行中的一些笨拙之处确实仍然存在——工作流仍然没有明确提示你应该在填充关卡之前先构建精灵和实体，我得自己摸索才发现这一点。这更像是基础模型产品直觉上的差距，而非 harness 设计旨在解决的问题，不过它确实暗示了一个可以通过 harness 内部的定向迭代来进一步提升输出质量的切入点。

在操作各编辑器的过程中，新运行相比单代理的优势变得更加明显。精灵编辑器更加丰富、功能更完善，工具面板更清晰，颜色选择器更好用，缩放控制更顺手。

因为我要求规划器在规格中融入 AI 功能，应用还内置了 Claude 集成，让我能通过提示词生成游戏的不同部分。这显著加快了工作流。

最大的差异体现在播放模式上。我终于能够移动实体并实际游玩游戏了。物理效果有些粗糙——我的角色跳上平台后会与平台重叠，直觉上感觉不对——但核心功能是工作的，而单代理运行连这一点都没做到。移动了一阵之后，我确实遇到了 AI 构建游戏关卡的一些限制。有一面大墙我无法跳过，所以我卡住了。这表明还有一些常识性的改进和边缘情况是 harness 可以处理以进一步优化应用的。

阅读日志后可以清楚看到，评估器使实现与规格保持了一致。每个冲刺中，它逐步检查冲刺合同的测试标准，通过 Playwright 操作运行中的应用，对任何偏离预期行为的问题提交 bug。合同粒度很细——仅 Sprint 3 就有 27 条标准覆盖关卡编辑器——评估器的发现足够具体，可以直接采取行动，无需额外调查。下表展示了几项评估器识别出的问题示例：

| **合同标准** | **评估器发现** |
| --- | --- |
| 矩形填充工具允许点击拖拽以选定瓦片填充矩形区域 | **失败** — 工具仅在拖拽起点/终点放置瓦片，而非填充整个区域。`fillRectangle` 函数存在但未在 mouseUp 时正确触发。 |
| 用户可以选择并删除已放置的实体生成点 | **失败** — `LevelEditor.tsx:892` 处的 Delete 键处理程序要求同时设置 `selection` 和 `selectedEntityId`，但点击实体只设置了 `selectedEntityId`。条件应为 `selection \|\| (selectedEntityId && activeLayer === 'entity')`。 |
| 用户可以通过 API 重排动画帧 | **失败** — `PUT /frames/reorder` 路由定义在 `/{frame_id}` 路由之后。FastAPI 将 'r`eorder`' 匹配为 frame_id 整数并返回 422："unable to parse string as an integer." |

让评估器达到这个水平需要不少功夫。开箱即用时，Claude 不是一个合格的 QA 代理。在早期运行中，我看着它识别出合理的问题，然后又说服自己这些问题不严重，最终还是批准了工作。它还倾向于做表面测试而非深入探测边缘情况，因此更隐蔽的 bug 往往溜了过去。调优循环是：阅读评估器日志，找出其判断与我的判断不一致的案例，然后更新 QA 的提示词来解决这些问题。经过多轮这样的开发循环后，评估器的评分才达到我认为合理的水平。即便如此，harness 的输出仍然暴露了模型 QA 能力的局限：小的布局问题、某些地方不够直观的交互，以及在更深层嵌套功能中评估器未充分测试而遗漏的 bug。显然还有更多的验证空间可以通过进一步调优来捕获。但与单代理运行中应用的核心功能根本无法工作相比，提升是显而易见的。

### 迭代 Harness

第一批 harness 的结果令人鼓舞，但它也显得笨重、缓慢且昂贵。合理的下一步是寻找简化 harness 的方法，同时不降低其性能。这部分是常识判断，部分则基于一个更普遍的原则：harness 中的每个组件都编码了一个关于模型自身无法完成某事的假设，而这些假设值得进行压力测试——既因为它们可能是不正确的，也因为它们会随着模型改进而迅速过时。我们的博客文章[构建有效的代理](https://www.anthropic.com/research/building-effective-agents)将这一底层思想概括为"找到尽可能简单的解决方案，仅在必要时才增加复杂度"，这一模式对于任何维护 agent harness 的人来说都反复出现。

在我第一次简化的尝试中，我大幅削减了 harness 并尝试了一些创造性的新想法，但未能复现原始版本的性能。要判断 harness 设计中哪些部分实际上是关键承重结构，以及它们以何种方式承重，也变得很困难。基于这一经验，我转向了更系统化的方法——一次移除一个组件，然后审查其对最终结果的影响。

在迭代过程中，我们还发布了 Opus 4.6，这进一步推动了减少 harness 复杂度的动机。有充分的理由预期 4.6 比 4.5 需要更少的脚手架。我们的[发布博客](https://www.anthropic.com/news/claude-opus-4-6)中写道："[Opus 4.6] 规划更周密，能更长时间地维持代理任务，在更大代码库中运行更可靠，并具备更好的代码审查和调试能力来发现自身错误。"它在长上下文检索方面也有大幅提升。这些都是 harness 原本用来补充的能力。

### 移除冲刺结构

我首先完全移除了冲刺结构。冲刺结构曾帮助将工作分解为模型能够连贯处理的块。鉴于 Opus 4.6 的改进，有充分理由相信模型可以原生地处理这项工作，无需此类分解。

我保留了规划器和评估器，因为它们各自仍然在提供明显的价值。没有规划器，生成器的范围会偏小：面对原始提示词，它会跳过先编写规格的步骤直接开始构建，最终产出的应用功能不如规划器丰富。

移除冲刺结构后，我将评估器改为在运行结束时进行一次性评估，而非按冲刺逐个评分。由于模型能力大幅提升，评估器在某些运行中的关键性发生了变化，其有用程度取决于任务相对于模型独立可靠完成能力的位置。在 4.5 上，这一边界很近：我们的构建正处于生成器独立完成能力的边缘，评估器在整个构建过程中捕获了有意义的问题。在 4.6 上，模型的原始能力提升了，边界外移。过去需要评估器检查才能连贯实现的任务，现在往往已处于生成器独立就能胜任的范围之内；对于这些边界内的任务，评估器变成了不必要的开销。但对于仍处于生成器能力边缘的构建部分，评估器仍然提供了实质性的提升。

实际意义在于，评估器并非一个固定的有或无的决策。当任务超出当前模型独立可靠完成的范围时，评估器的成本是值得的。

在结构简化的同时，我还增加了提示词来改进 harness 在每个应用中构建 AI 功能的方式，具体来说，让生成器构建一个能够通过工具驱动应用自身功能的正式代理。这需要真正的迭代，因为相关知识足够新，Claude 的训练数据覆盖较薄。但经过足够的调优，生成器能够正确地构建代理了。

### 更新后 Harness 的结果

为了测试更新后的 harness，我使用以下提示词生成一个数字音频工作站（DAW）——一个用于作曲、录制和混音的音乐制作程序：

> _在浏览器中使用 Web Audio API 构建一个功能完备的 DAW。_

运行仍然耗时且昂贵，大约 4 小时，token 成本为 $124。

大部分时间花在构建器上，它在没有 Opus 4.5 所需的冲刺分解的情况下，连贯地运行了超过两个小时。

| **代理与阶段** | **时长** | **成本** |
| --- | --- | --- |
| 规划器 | 4.7 分钟 | $0.46 |
| 构建（第 1 轮） | 2 小时 7 分钟 | $71.08 |
| QA（第 1 轮） | 8.8 分钟 | $3.24 |
| 构建（第 2 轮） | 1 小时 2 分钟 | $36.89 |
| QA（第 2 轮） | 6.8 分钟 | $3.09 |

| QA（第 3 轮） | 9.6 分钟 | $4.06 |
| **V2 Harness 总计** | **3 小时 50 分钟** | **$124.70** |

与之前的 harness 一样，规划器将一行提示词扩展为完整的规格。从日志中可以看到，生成器模型在应用规划和代理设计方面做得很好，完成了代理的连接和测试，然后交接给 QA。

尽管如此，QA 代理仍然捕获了真实的缺陷。在第一轮反馈中，它指出：

> 这是一个设计保真度出色、AI 代理扎实、后端良好的强应用。主要的失败点在于功能完整性——虽然应用看起来令人印象深刻，AI 集成也运作良好，但几个核心 DAW 功能仅停留在展示层面，缺乏交互深度：片段无法在时间轴上拖拽/移动，没有乐器 UI 面板（合成器旋钮、鼓垫），也没有可视化的效果编辑器（EQ 曲线、压缩器表盘）。这些不是边缘情况——它们是让 DAW 真正可用的核心交互，而规格中明确要求了这些功能。

在第二轮反馈中，它再次捕获了多项功能缺失：

> 剩余缺口：
>
> - 音频录制仍只是桩代码（按钮切换但没有麦克风捕获）
>
> - 片段边缘拖拽调整大小和片段分割未实现
>
> - 效果可视化是数字滑块，而非图形化（没有 EQ 曲线）

生成器在无人监督时仍然容易遗漏细节或将功能停留在桩代码阶段，QA 在捕获这些最后一公里问题以供生成器修复方面仍然提供了价值。

根据提示词，我期望的是一个能创建旋律、和声和鼓点模式，将它们编排成一首歌曲，并在此过程中获得集成代理帮助的程序。下面的视频展示了结果。

## 下一步

随着模型持续改进，我们可以大致预期它们能够工作更长时间，处理更复杂的任务。在某些情况下，这意味着围绕模型的脚手架随时间推移变得不那么重要，开发者可以等待下一个模型，看某些问题自行解决。另一方面，模型越强大，就有越多的空间来开发能够完成模型基线能力之外复杂任务的 harness。

基于这一认识，这项工作中有几点经验值得沿用。始终以你正在使用的模型进行实验，阅读其在真实问题上的执行轨迹，并调优其性能以达到期望的效果——这是好的实践。在处理更复杂的任务时，通过分解任务并对问题的各个方面应用专门的代理，有时可以获得额外的提升空间。而当新模型发布时，重新审视 harness、剥离不再对性能关键承重的部分，并添加新的组件以实现此前不可能达到的更高能力，通常是好的做法。

从这项工作中，我的信念是：有趣的 harness 组合空间并不会随着模型改进而缩小。相反，它在移动，而 AI 工程师有趣的工作就是持续寻找下一个新颖的组合。
