# 构建高效的 AI 代理

### 代理

随着 LLM 在理解复杂输入、进行推理和规划、可靠地使用工具以及从错误中恢复等关键能力上的日趋成熟，代理正在生产环境中逐步落地。代理的工作始于人类用户的指令或交互式对话。一旦任务明确，代理便会独立进行规划和执行，必要时可能回头向人类寻求更多信息或判断。在执行过程中，代理必须在每一步从环境中获取“真实依据”（例如工具调用结果或代码执行结果）以评估自身进展，这一点至关重要。随后，代理可以在检查点处暂停以获取人类反馈，或在遇到阻碍时请求帮助。任务通常在完成时终止，但设置停止条件（例如最大迭代次数）以保持控制也是很常见的做法。

代理可以处理复杂任务，但其实现往往并不复杂。它们通常只是 LLM 在循环中根据环境反馈使用工具而已。因此，精心设计工具集及其文档至关重要。我们在附录 2（"为你的工具做提示词工程"）中详细阐述了工具开发的最佳实践。

**何时使用代理：** 代理适用于开放性问题，在这类问题中很难或无法预测所需的步骤数，也无法硬编码固定路径。LLM 可能需要运行多个回合，因此你必须对其决策能力有一定程度的信任。代理的自主性使其非常适合在可信环境中规模化处理任务。

代理的自主性意味着更高的成本，以及错误累积放大的风险。我们建议在沙箱环境中进行大量测试，并配备适当的安全护栏。

**代理适用的场景示例：**

以下示例来自我们的实际实现：

## 组合与自定义这些模式

这些构建模块并非强制性规范。它们是开发者可以根据不同用例进行塑造和组合的常见模式。与任何 LLM 功能一样，成功的关键在于衡量性能并迭代实现方式。再次强调：只有当增加复杂性确实能改善结果时，才应该考虑这样做。

## 总结

在 LLM 领域取得成功，不在于构建最复杂的系统，而在于构建最适合你需求的系统。从简单的提示词开始，通过全面的评估进行优化，只有当更简单的方案不够用时，才引入多步代理系统。

在实现代理时，我们尽量遵循三个核心原则：

1.   在代理设计中保持**简洁性**。
2.   通过明确展示代理的规划步骤来优先考虑**透明性**。
3.   通过充分的工具**文档编写和测试**来精心设计代理-计算机接口（ACI）。

框架可以帮助你快速上手，但在走向生产环境时，不要犹豫减少抽象层，使用基础组件来构建。遵循这些原则，你可以创建出不仅功能强大，而且可靠、可维护，并赢得用户信任的代理。

## 附录 1：代理的实践应用

我们与客户的合作揭示了 AI 代理的两个特别有前景的应用方向，它们展示了上述讨论模式的实际价值。这两个应用都说明，代理在以下任务中最能发挥价值：需要同时具备对话和行动能力、有明确的成功标准、能够形成反馈闭环，并融入有意义的人工监督。

### A. 客户支持

客户支持将常见的聊天机器人界面与通过工具集成增强的功能相结合。这对于更开放式的代理来说是天然的契合场景，因为：

*   支持交互天然遵循对话流程，同时需要访问外部信息和执行操作；
*   可以集成工具来拉取客户数据、订单历史和知识库文章；
*   退款发放或工单更新等操作可以通过程序化方式处理；
*   成功与否可以通过用户定义的解决结果来明确衡量。

多家公司已通过按效果付费的定价模式证明了这种方法的可行性——仅在问题成功解决时才收费，这表明了他们对代理效果的信心。

### B. 编程代理

软件开发领域展现了 LLM 功能的巨大潜力，能力已从代码补全演进到自主问题解决。代理尤其有效，因为：

*   代码解决方案可以通过自动化测试来验证；
*   代理可以利用测试结果作为反馈来迭代优化解决方案；
*   问题空间定义明确且结构化；
*   输出质量可以客观衡量。

在我们自己的实现中，代理现在仅凭 pull request 描述就能解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准测试中真实的 GitHub 问题。然而，虽然自动化测试有助于验证功能，但人工审查对于确保解决方案符合更广泛的系统需求仍然至关重要。

## 附录 2：为你的工具做提示词工程

无论你构建的是哪种代理系统，工具都可能是代理的重要组成部分。[工具](https://www.anthropic.com/news/tool-use-ga)使 Claude 能够通过在我们的 API 中指定其确切结构和定义来与外部服务和 API 进行交互。当 Claude 响应时，如果它计划调用某个工具，会在 API 响应中包含一个[工具使用块](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具的定义和规范应该获得与整体提示词同等程度的提示词工程关注。在这个简短的附录中，我们将介绍如何为工具做提示词工程。

指定同一操作往往有多种方式。例如，你可以通过编写 diff 来指定文件编辑，也可以通过重写整个文件。对于结构化输出，你可以在 markdown 中返回代码，也可以在 JSON 中返回。在软件工程中，这些差异只是表面形式，可以无损地互相转换。然而，某些格式对 LLM 来说比其他格式难写得多。编写 diff 需要在编写新代码之前就知道代码块头部中有多少行正在更改。在 JSON 中编写代码（与 markdown 相比）需要额外转义换行符和引号。

我们关于选择工具格式的建议如下：

*   给模型足够的 token 来"思考"，避免它把自己逼入死角。
*   保持格式接近模型在互联网文本中自然看到的形式。
*   确保没有格式上的"额外负担"，比如需要准确计算数千行代码的数量，或对编写的代码进行字符串转义。

一个经验法则是：想想在人机交互界面（HCI）上投入了多少精力，然后计划在创建良好的_代理_-计算机接口（ACI）上投入同等的精力。以下是一些具体建议：

*   设身处地站在模型的角度。根据描述和参数，这个工具的用法是否一目了然，还是需要仔细思考？如果需要仔细思考，模型很可能也是如此。一个好的工具定义通常包含使用示例、边界情况、输入格式要求，以及与其他工具的明确界限。
*   如何调整参数名称或描述使事情更直观？把这想象成在为团队中的初级开发者编写优秀的文档字符串。当使用许多相似的工具时，这一点尤为重要。
*   测试模型如何使用你的工具：在我们的[工作台](https://console.anthropic.com/workbench)中运行大量示例输入，观察模型犯了哪些错误，然后进行迭代。
*   对你的工具进行[防错设计](https://en.wikipedia.org/wiki/Poka-yoke)。调整参数，使犯错变得更困难。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建代理时，我们实际上花在优化工具上的时间比花在整体提示词上的时间更多。例如，我们发现当代理离开根目录后，使用相对文件路径的工具容易出错。为了解决这个问题，我们将工具改为始终要求绝对文件路径——我们发现模型使用这种方式完美无缺。
