# 深入理解 AI 代理的评估

## 引言

良好的评估能帮助团队更自信地交付 AI 代理。没有评估，团队很容易陷入被动循环——只在生产环境中发现问题，而修复一个故障又会引发其他故障。评估让问题和行为变化在影响用户之前变得可见，其价值在代理的整个生命周期中不断累积。

正如我们在[构建有效的代理](https://www.anthropic.com/engineering/building-effective-agents)中所述，代理在多轮交互中运行：调用工具、修改状态、根据中间结果进行调整。正是这些让 AI 代理变得有用的能力——自主性、智能性和灵活性——也让它们更难被评估。

通过我们的内部工作以及与前沿代理开发客户的合作，我们学会了如何为代理设计更严谨、更实用的评估。以下是我们在实际部署中，经过多种代理架构和使用场景验证的有效方法。

## 评估的结构

**评估**（eval）是对 AI 系统的测试：向 AI 提供输入，然后对其输出应用评分逻辑来衡量成功与否。本文重点关注可以在开发过程中无需真实用户即可运行的**自动化评估**。

**单轮评估**很简单：一个提示词、一个响应和评分逻辑。对于早期的 LLM，单轮非代理评估是主要的评估方法。随着 AI 能力的进步，**多轮评估**变得越来越普遍。

![Image 1](assets/001-image-1-efa20fe651.png)

在简单的评估中，代理处理一个提示词，评分器检查输出是否符合预期。在更复杂的多轮评估中，一个编码代理接收工具、任务（本例中是构建一个 MCP 服务器）和环境，执行"代理循环"（工具调用和推理），并更新环境以实现功能。然后通过单元测试来验证可正常工作的 MCP 服务器。

**代理评估**则更加复杂。代理在多轮交互中使用工具，在过程中修改环境状态并不断适应——这意味着错误可以传播和累积。前沿模型还能找到超越静态评估限制的创造性解决方案。例如，Opus 4.5 通过[发现](https://www.anthropic.com/news/claude-opus-4-5)政策中的漏洞，解决了一个关于预订航班的 [𝜏2-bench](https://github.com/sierra-research/tau2-bench) 问题。按照原始评估标准它"失败"了，但实际上为用户提供了更好的解决方案。

在构建代理评估时，我们使用以下定义：

*   **任务**（也称**问题**或**测试用例**）是一个具有明确输入和成功标准的单次测试。
*   每次尝试完成一个任务称为一次**试验**。由于模型输出在每次运行中会有所不同，我们通过多次试验来获得更一致的结果。
*   **评分器**是对代理表现某方面进行评分的逻辑。一个任务可以有多个评分器，每个评分器包含多个断言（有时称为**检查**）。
*   **记录**（也称**轨迹**）是一次试验的完整记录，包括输出、工具调用、推理、中间结果和所有其他交互。对于 Anthropic API，这是评估运行结束时的完整消息数组——包含评估期间所有 API 调用和所有返回的响应。
*   **结果**是试验结束时环境中的最终状态。一个航班预订代理可能在记录末尾说"您的航班已预订"，但结果是环境的 SQL 数据库中是否存在预订记录。
*   **评估 harness** 是端到端运行评估的基础设施。它提供指令和工具，并发运行任务，记录所有步骤，对输出进行评分并汇总结果。
*   **代理 harness**（或称**脚手架**）是使模型能够作为代理行动的系统：它处理输入、编排工具调用并返回结果。当我们评估"一个代理"时，我们实际上在评估 harness 和模型的协同工作。例如，[Claude Code](https://claude.com/product/claude-code) 是一个灵活的代理 harness，我们通过 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 使用其核心原语构建了[长时间运行的代理 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
*   **评估套件**是一组旨在衡量特定能力或行为的任务集合。套件中的任务通常共享一个广泛的目标。例如，一个客户支持评估套件可能测试退款、取消和升级处理。

## 为什么要构建评估？

当团队刚开始构建代理时，通过手工测试、[内部试用](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)和直觉的组合，往往能取得令人惊讶的进展。更严谨的评估甚至可能看起来是拖慢交付速度的额外开销。但在早期原型阶段之后，一旦代理进入生产环境并开始扩展，没有评估的开发就会开始出问题。

转折点通常出现在用户报告代理在修改后变差了，而团队却在"盲飞"——除了猜测和验证之外没有其他方法来确认问题。没有评估，调试是被动的：等待投诉、手动复现、修复 bug，然后祈祷没有其他功能回归。团队无法区分真正的功能退化和噪音，无法在发布前自动测试数百个场景，也无法衡量改进效果。

我们曾多次看到这种演变过程。例如，Claude Code 最初通过 Anthropic 员工和外部用户的反馈进行快速迭代。后来，我们添加了评估——首先是针对简洁性和文件编辑等狭窄领域，然后是过度工程等更复杂的行为。这些评估帮助识别问题、指导改进，并聚焦研究与产品团队的合作。结合生产监控、A/B 测试、用户研究等手段，评估提供了持续改进 Claude Code 随其规模化发展所需的信号。

在代理生命周期的任何阶段编写评估都很有价值。早期，评估促使产品团队明确代理的成功标准；后期，它们帮助维持一致的质量标准。

[Descript](https://www.descript.com/) 的代理帮助用户编辑视频，因此他们围绕成功编辑工作流的三个维度构建了评估：不要破坏东西、做我要求的、做好它。他们从手工评分发展到由产品团队定义标准并由人工定期校准的 LLM 评分器，现在定期运行两套独立的评估套件分别用于质量基准测试和回归测试。[Bolt](https://bolt.new/) AI 团队在已经拥有广泛使用的代理之后才开始构建评估。在 3 个月内，他们构建了一个评估系统，使用静态分析运行代理并评分输出，使用浏览器代理测试应用，并使用 LLM 评审来评估指令遵循等行为。

有些团队在开发之初就创建评估；其他团队则在规模化后、评估成为改进代理的瓶颈时才添加。评估在代理开发之初尤其有用，可以明确编码预期行为。两个工程师阅读同一份初始规范，可能对 AI 应如何处理边缘情况有不同理解。评估套件可以消除这种歧义。无论何时创建，评估都有助于加速开发。

评估还影响你采用新模型的速度。当更强大的模型发布时，没有评估的团队面临数周的测试，而有评估的竞争团队可以快速确定模型的优势、调整提示词并在几天内完成升级。

一旦有了评估，你就能免费获得基线和回归测试：延迟、token 用量、每任务成本和错误率可以在固定的任务集上进行追踪。评估还可以成为产品团队和研究团队之间最高带宽的沟通渠道，定义研究人员可以优化的指标。显然，评估的好处远不止追踪回归和改进。其累积价值很容易被忽视，因为成本是前期可见的，而收益则是后期逐步积累的。

## 如何评估 AI 代理

目前大规模部署的常见代理类型包括编码代理、研究代理、计算机使用代理和对话代理。每种类型可能部署在各种行业中，但可以使用类似的技术进行评估。你不需要从零开始发明评估方法。以下各节描述了针对多种代理类型的经过验证的技术。以这些方法为基础，然后扩展到你的领域。

### 代理的评分器类型

代理评估通常结合三种类型的评分器：基于代码的、基于模型的和人工评分器。每种评分器评估记录或结果的某个部分。有效评估设计的关键组成部分是为任务选择合适的评分器。

基于代码的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| • 字符串匹配检查（精确匹配、正则、模糊匹配等） • 二元测试（从失败到通过、从通过到通过） • 静态分析（lint、类型检查、安全检查） • 结果验证 • 工具调用验证（使用的工具、参数） • 记录分析（交互轮数、token 用量） | • 快速 • 便宜 • 客观 • 可复现 • 易于调试 • 验证特定条件 | • 对不完全匹配预期模式的有效变体较为脆弱 • 缺乏细微判断 • 评估某些主观任务的能力有限 |

基于模型的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| * 基于评分标准的评分 * 自然语言断言 * 成对比较 * 基于参考的评估 * 多评审共识 | * 灵活 * 可扩展 * 能捕捉细微差别 * 处理开放式任务 * 处理自由格式输出 | * 非确定性 * 比代码评分更贵 * 需要与人工评分器校准以确保准确性 |

人工评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| * 领域专家评审 * 众包评判 * 抽样检查 * A/B 测试 * 标注者间一致性 | * 黄金标准质量 * 匹配专家用户判断 * 用于校准基于模型的评分器 | * 昂贵 * 缓慢 * 通常需要大规模的人工专家参与 |

对于每个任务，评分可以是加权的（组合评分器分数需达到阈值）、二元的（所有评分器都必须通过）或混合的。

### 能力评估与回归评估

**能力评估**（也称"质量"评估）问的是"这个代理擅长做什么？"它们应该以较低的通过率开始，聚焦于代理难以处理的任务，给团队一个攀登的目标。

**回归评估**问的是"代理是否仍然能处理以前能处理的所有任务？"其通过率应该接近 100%。它们防止功能倒退，因为分数下降意味着有什么出了问题需要改进。当团队在能力评估上不断攀升时，同时运行回归评估也很重要，以确保更改不会在其他地方引发问题。

当代理上线并优化后，通过率很高的能力评估可以"毕业"成为持续运行的回归套件，以捕获任何漂移。曾经衡量"我们是否能做到"的任务，转而衡量"我们是否仍然能可靠地做到"。

### 评估编码代理

**编码代理**编写、测试和调试代码，像人类开发者一样在代码库中导航并运行命令。有效的现代编码代理评估通常依赖于定义明确的任务、稳定的测试环境和对生成代码的全面测试。

确定性评分器天然适合编码代理，因为软件通常很容易评估：代码能否运行，测试是否通过？两个广泛使用的编码代理基准测试，[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)，都采用了这种方法。SWE-bench Verified 给代理来自热门 Python 仓库的 GitHub issue，通过运行测试套件来评分解决方案；只有当解决方案修复了失败的测试而不破坏现有测试时才算通过。LLM 在仅仅一年内将该评估的得分从 40% 提升到了 >80%。Terminal-Bench 采用了不同的路径：它测试端到端的技术任务，例如从源代码构建 Linux 内核或训练 ML 模型。

一旦你有了一套用于验证编码任务关键**结果**的通过/失败测试，通常还需要对**记录**进行评分。例如，基于启发式的代码质量规则可以不仅仅根据通过的测试来评估生成的代码，具有明确评分标准的基于模型的评分器可以评估代理如何调用工具或与用户交互等行为。

**示例：编码代理的理论评估**

考虑一个编码任务，代理必须修复一个身份验证绕过漏洞。如下面示意性的 YAML 文件所示，可以使用评分器和指标来评估此代理。

```
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

请注意，此示例展示了可用评分器的完整范围仅供说明。在实践中，编码评估通常依赖单元测试进行正确性验证，使用 LLM 评分标准评估整体代码质量，仅在需要时添加额外的评分器和指标。

### 评估对话代理

**对话代理**在支持、销售或辅导等领域与用户交互。与传统的聊天机器人不同，它们维护状态、使用工具，并在对话过程中执行操作。虽然编码和研究代理也可能涉及与用户的多轮交互，但对话代理呈现了一个独特的挑战：交互质量本身就是你要评估的一部分。有效的对话代理评估通常依赖于可验证的最终状态结果和同时涵盖任务完成度与交互质量的评分标准。与大多数其他评估不同，它们通常需要第二个 LLM 来模拟用户。我们在[对齐审计代理](https://alignment.anthropic.com/2025/automated-auditing/)中使用这种方法，通过长时间的对抗性对话来压力测试模型。

对话代理的成功可以有多维度衡量：工单是否解决（状态检查）、是否在 10 轮内完成（记录约束）、语气是否恰当（LLM 评分标准）？包含多维度的两个基准测试是 [𝜏-Bench](https://arxiv.org/abs/2406.12045) 及其后续版本 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们模拟零售支持和航空预订等领域的多轮交互，一个模型扮演用户角色，代理应对各种真实场景。

**示例：对话代理的理论评估**

考虑一个支持任务，代理必须处理一位沮丧客户的退款请求。

```
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

与编码代理示例一样，此任务展示了多种评分器类型仅供说明。在实践中，对话代理评估通常使用基于模型的评分器来评估沟通质量和目标完成度，因为许多任务（如回答问题）可能有多种"正确"解决方案。

### 评估研究代理

**研究代理**收集、综合和分析信息，然后产生答案或报告等输出。与编码代理通过单元测试提供二元通过/失败信号不同，研究质量只能相对于任务来判断。什么算作"全面"、"有充分来源"甚至"正确"，取决于上下文：市场扫描、收购的尽职调查和科学报告各自需要不同的标准。

研究评估面临独特的挑战：专家可能对综合是否全面存在分歧，随着参考内容的不断变化，真实答案也在不断漂移，更长、更开放式的输出为错误创造了更多空间。例如，像 [BrowseComp](http://arxiv.org/abs/2504.12516) 这样的基准测试，测试 AI 代理能否在开放网络的大海中找到针——问题设计得易于验证但难以解决。

构建研究代理评估的一种策略是组合评分器类型。依据性检查验证声明是否有检索到的来源支持，覆盖度检查定义一个好的答案必须包含的关键事实，来源质量检查确认所参考的来源是否权威，而不仅仅是首先检索到的那些。对于有客观正确答案的任务（"公司 X 第三季度的收入是多少？"），精确匹配即可。LLM 可以标记没有依据的声明和覆盖范围的差距，也可以验证开放式综合的连贯性和完整性。

鉴于研究质量的主观性，基于 LLM 的评分标准应经常与专家人工判断进行校准，以有效地对这些代理进行评分。

### 计算机使用代理

**计算机使用代理**通过与人类相同的界面与软件交互——截图、鼠标点击、键盘输入和滚动——而不是通过 API 或代码执行。它们可以使用任何具有图形用户界面（GUI）的应用程序，从设计工具到传统企业软件。评估需要在真实或沙箱环境中运行代理，让它使用软件应用程序，然后检查是否达到了预期结果。例如，[WebArena](https://arxiv.org/abs/2307.13854) 测试基于浏览器的任务，使用 URL 和页面状态检查来验证代理是否正确导航，以及用于修改数据任务的后端状态验证（确认订单确实已下单，而不仅仅是确认页面出现了）。[OSWorld](https://os-world.github.io/) 将此扩展到完整的操作系统控制，评估脚本在任务完成后检查各种产物：文件系统状态、应用程序配置、数据库内容和 UI 元素属性。

浏览器使用代理需要在 token 效率和延迟之间取得平衡。基于 DOM 的交互执行速度快但消耗大量 token，而基于截图的交互较慢但更省 token。例如，当要求 Claude 总结维基百科时，从 DOM 中提取文本更高效。当在亚马逊上寻找新的笔记本电脑保护套时，截图更高效（因为提取整个 DOM 非常消耗 token）。在我们的 Claude for Chrome 产品中，我们开发了评估来检查代理是否为每种上下文选择了正确的工具。这使我们能够更快、更准确地完成基于浏览器的任务。

### 如何看待代理评估中的非确定性

无论代理类型如何，代理行为在各次运行之间会有所不同，这使得评估结果比表面上看起来更难解读。每个任务都有自己的成功率——可能一个任务 90%，另一个 50%——而在一次评估运行中通过的任务在下一次可能会失败。有时，我们想衡量的是代理在某个任务上成功的**频率**（试验的比例）。

两个指标有助于捕捉这种细微差别：

[**pass@k**](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 衡量代理在 _k_ 次尝试中至少获得一个正确解决方案的可能性。随着 _k_ 的增加，pass@k 分数上升：更多的"尝试机会"意味着至少成功一次的概率更高。50% 的 pass@1 分数意味着模型在第一次尝试中成功完成了一半的评估任务。在编码中，我们通常最关心代理是否能在第一次就找到解决方案——pass@1。在其他情况下，提出多个解决方案只要有一个有效即可。

[**pass^k**](https://arxiv.org/abs/2406.12045) 衡量所有 _k_ 次试验都成功的概率。随着 _k_ 的增加，pass^k 下降，因为要求在更多试验中保持一致是一个更高的标准。如果你的代理每次试验的成功率为 75%，你运行 3 次试验，那么三次全部通过的概率是 (0.75)³ ≈ 42%。此指标对于面向用户的代理尤为重要，因为用户期望每次行为都可靠。

![Image 3](assets/003-image-3-7a642749ee.png)

pass@k 和 pass^k 随着试验次数增加而发散。在 k=1 时，它们完全相同（都等于每次试验的成功率）。到 k=10 时，它们讲述着相反的故事：pass@k 接近 100%，而 pass^k 降至 0%。

两个指标都很有用，选择哪个取决于产品需求：pass@k 适用于一次成功就重要的工具，pass^k 适用于一致性至关重要的代理。

## 从零到一：构建出色代理评估的路线图

本节概述了我们经过实践检验的建议，帮助你从没有评估到拥有可信的评估。将此视为评估驱动的代理开发路线图：尽早定义成功标准，清晰地衡量它，并持续迭代。

### 收集初始评估数据集的任务

**第 0 步：尽早开始**

我们看到团队因为认为需要数百个任务而推迟构建评估。实际上，从真实故障中提取的 20-50 个简单任务就是一个很好的起点。毕竟，在早期代理开发中，系统的每次更改通常都有明显的影响，这种大效应量意味着小样本就足够了。更成熟的代理可能需要更大、更难的评估来检测更小的效应，但最好在开始时采用 80/20 的方法。评估等待时间越长就越难构建。早期，产品需求自然转化为测试用例。等太久，你就要从运行中的系统逆向工程成功标准了。

**第 1 步：从你已经在手动测试的内容开始**

从你在开发过程中运行的手动检查开始——每次发布前验证的行为和最终用户尝试的常见任务。如果你已经在生产环境中，查看你的 bug 追踪器和支持队列。将用户报告的故障转化为测试用例，确保你的套件反映实际使用情况；按用户影响优先排序有助于将精力投入到最重要的地方。

**第 2 步：编写明确无歧义的任务和参考解决方案**

确保任务质量比看起来更难。一个好的任务是两个领域专家可以独立做出相同通过/失败判断的任务。他们自己能否通过这个任务？如果不能，任务就需要改进。任务规范中的歧义会变成指标中的噪音。这同样适用于基于模型的评分器的标准：模糊的评分标准会产生不一致的判断。

每个任务都应该可以被正确遵循指令的代理通过。这可能很微妙。例如，审计 Terminal-Bench 发现，如果任务要求代理编写脚本但没有指定文件路径，而测试假设脚本位于特定路径，代理可能并非因为自身错误而失败。评分器检查的所有内容都应该在任务描述中明确；代理不应因为模糊的规范而失败。对于前沿模型，多次试验中的 0% 通过率（即 0% pass@100）通常是任务有问题的信号，而不是代理能力不足，也是重新检查任务规范和评分器的提示。对于每个任务，创建一个参考解决方案很有用：一个已知可以工作的、通过所有评分器的输出。这证明了任务是可解决的，并验证评分器配置正确。

**第 3 步：构建平衡的问题集**

同时测试行为**应该**发生和**不应该**发生的情况。单方面的评估会导致单方面的优化。例如，如果你只测试代理是否在应该搜索时进行了搜索，你最终可能得到一个几乎什么都搜索的代理。尽量避免[类别不平衡](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评估。我们在为 [Claude.ai](http://claude.ai/redirect/website.v1.a9f96f47-56bb-49e9-a1fd-f56c0c749d1f) 构建网页搜索评估时深有体会。挑战在于防止模型在不应该搜索时搜索，同时保留其在适当时进行广泛研究的能力。团队构建了覆盖两个方向的评估：模型应该搜索的查询（如查找天气）和应该从现有知识回答的查询（如"谁创立了苹果公司？"）。在触发不足（应该搜索时不搜索）和过度触发（不应该搜索时搜索）之间取得正确平衡很困难，需要对提示词和评估进行多轮调整。随着更多示例问题的出现，我们继续向评估中添加内容以改善覆盖范围。

### 设计评估 harness 和评分器

**第 4 步：构建具有稳定环境的健壮评估 harness**

评估中的代理应该与生产中使用的代理大致相同地运行，环境本身不应引入额外的噪音。每次试验应通过从干净环境启动来"隔离"。运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能因基础设施的不稳定而非代理性能导致相关故障。共享状态还可能人为地提高性能。例如，在一些内部评估中，我们观察到 Claude 通过检查之前试验的 git 历史在某些任务上获得了不公平的优势。如果多个不同的试验因环境的相同限制（如 CPU 内存有限）而失败，这些试验不是独立的，因为它们受到相同因素的影响，评估结果对衡量代理性能就变得不可靠了。

**第 5 步：精心设计评分器**

如上所述，出色的评估设计涉及为代理和任务选择最佳评分器。我们建议在可能的情况下选择确定性评分器，在需要额外灵活性时使用 LLM 评分器，并审慎使用人工评分器进行额外验证。

有一种常见的本能是检查代理是否遵循了非常具体的步骤，如按正确顺序的工具调用序列。我们发现这种方法过于僵化，导致测试过于脆弱，因为代理经常找到评估设计者没有预料到的有效方法。为了避免不必要地惩罚创造力，通常更好的做法是评估代理产生了什么，而不是它走了什么路径。

对于包含多个组件的任务，构建部分计分**。**一个正确识别问题并验证客户但未能处理退款的支持代理，明显比一个立即失败的代理要好。在结果中体现这种成功的连续性很重要。

模型评分通常需要仔细迭代以验证准确性。LLM 评审评分器应与人类专家密切校准，以确信人工评分和模型评分之间几乎没有分歧。为避免幻觉，给 LLM 一个退路，比如提供一条在信息不足时返回 "Unknown" 的指令。创建清晰、结构化的评分标准来评估任务的每个维度，然后使用独立的 LLM 评审来评估每个维度，而不是用一个来评估所有维度，这也很有帮助。一旦系统足够健壮，仅偶尔使用人工审查即可。

有些评估有微妙的故障模式，即使代理表现良好也会导致低分，因为代理由于评分 bug、代理 harness 限制或歧义而无法解决任务。即使是经验丰富的团队也可能忽略这些问题。例如，[Opus 4.5 在 CORE-Bench 上的初始得分只有 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，直到一位 Anthropic 研究员发现了多个问题：僵化的评分在期望"96.124991..."时惩罚了"96.12"，模糊的任务规范，以及无法精确复现的随机任务。在修复 bug 并使用限制更少的脚手架后，Opus 4.5 的得分跃升至 95%。类似地，[METR 发现](https://x.com/metr_evals/status/2001473506442375645?s=46)他们的时间范围基准测试中有几个配置错误的任务，要求代理优化到声明的分数阈值，但评分要求超过该阈值。这惩罚了像 Claude 这样遵循指令的模型，而忽略声明目标的模型反而获得了更好的分数。仔细检查任务和评分器有助于避免这些问题。

让你的评分器能够抵御绕过或黑客攻击。代理不应该能够轻易地"作弊"评估。任务和评分器的设计应确保通过确实需要解决问题，而不是利用意料之外的漏洞。

### 长期维护和使用评估

**第 6 步：检查记录**

除非你阅读多次试验的记录和评分，否则你不会知道评分器是否运行良好。在 Anthropic，我们投资了查看评估记录的工具，并定期花时间阅读它们。当任务失败时，记录告诉你代理是犯了真正的错误，还是你的评分器拒绝了一个有效的解决方案。它还经常揭示关于代理和评估行为的关键细节。

失败应该是公平的：代理哪里做错了、为什么错了应该是清楚的。当分数不再上升时，我们需要确信这是因为代理性能问题而不是评估的问题。阅读记录是你验证评估是否衡量了真正重要内容的方式，也是代理开发的关键技能。

**第 7 步：监控能力评估饱和度**

100% 的评估追踪回归但不提供改进信号。**评估饱和**发生在代理通过了所有可解决的任务，没有改进空间时。例如，SWE-Bench Verified 得分今年从 30% 起步，前沿模型现在已接近饱和的 >80%。随着评估接近饱和，进展也会放缓，因为只剩下最困难的任务。这可能使结果具有欺骗性，因为大幅的能力提升在分数上表现为小幅增长。例如，代码审查初创公司 [Qodo](https://www.qodo.ai/) 最初对 Opus 4.5 不以为然，因为他们的单次编码评估没有捕捉到在更长、更复杂任务上的提升。作为回应，他们开发了一个新的代理评估框架，提供了更清晰的进展图景。

通常，在有人深入研究评估细节并阅读一些记录之前，我们不会直接照单全收这些评估分数。如果评分不公平、任务有歧义、有效的解决方案被惩罚，或 harness 限制了模型，评估就应该被修订。

**第 8 步：通过开放贡献和维护保持评估套件的长期健康**

评估套件是一个需要持续关注和明确责任归属才能保持有用的活文档。

在 Anthropic，我们尝试了各种评估维护方法。最有效的是建立专门的评估团队负责核心基础设施，而领域专家和产品团队贡献大部分评估任务并自行运行评估。

对于 AI 产品团队，拥有和迭代评估应该像维护单元测试一样常规。团队可能在那些早期测试中看似"可用"、却无法满足未明说预期的 AI 功能上浪费数周时间，而精心设计的评估本可以及早暴露这些问题。定义评估任务是压力测试产品需求是否足够具体以开始构建的最佳方式之一。

我们建议实践评估驱动的开发：在代理能够实现计划功能之前构建评估来定义它们，然后迭代直到代理表现良好。在内部，我们经常构建今天"足够好"但在未来几个月模型能力提升时会有回报的功能。以低通过率开始的能力评估使这一点变得可见。当新模型发布时，运行评估套件可以快速揭示哪些投入得到了回报。

最接近产品需求和用户的人最适合定义成功标准。以当前的模型能力，产品经理、客户成功经理或销售人员可以使用 Claude Code 以 PR 的形式贡献评估任务——让他们来！或者更好的是，主动赋能他们。

## 评估与其他方法的结合：全面理解代理

自动化评估可以在数千个任务上运行，无需部署到生产环境或影响真实用户。但这只是理解代理性能的众多方式之一。完整的图景包括生产监控、用户反馈、A/B 测试、手动记录审查和系统性人工评估。

理解 AI 代理性能的方法概览

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| **自动化评估**_在没有真实用户的情况下以编程方式运行测试_ | * 更快的迭代 * 完全可复现 * 无用户影响 * 可以在每次提交时运行 * 无需生产部署即可大规模测试场景 | * 需要更多前期建设投入 * 需要随着产品和模型的演进持续维护以避免漂移 * 如果不匹配真实使用模式可能产生虚假信心 |
| **生产监控**_在实时系统中追踪指标和错误_ | * 揭示大规模的真实用户行为 * 捕获合成评估遗漏的问题 * 提供代理实际表现的真实数据 | * 被动的；问题到达用户之前你不知道 * 信号可能有噪音 * 需要基础设施投入 * 缺少评分的真实标准 |
| **A/B 测试**_用真实用户流量比较变体_ | * 衡量实际用户结果（留存率、任务完成率） * 控制混淆因素 * 可扩展且系统化 | * 慢；需要数天或数周才能达到显著性，且需要足够流量 * 只测试你部署的变更 * 在不彻底审查记录的情况下，对指标变化背后的"原因"信号较少 |
| **用户反馈**_明确信号如点踩或错误报告_ | * 发现你没想到的问题 * 附带真实用户的具体示例 * 反馈通常与产品目标相关 | * 稀少且自我选择 * 偏向严重问题 * 用户很少解释某事_为什么_失败了 * 非自动化 * 主要依靠用户发现问题可能对用户体验产生负面影响 |
| **手动记录审查**_人类阅读代理对话_ | * 建立对故障模式的直觉 * 捕获自动检查遗漏的细微质量问题 * 帮助校准什么是"好的"并掌握细节 | * 耗时 * 不可扩展 * 覆盖范围不一致 * 审查者疲劳或不同审查者可能影响信号质量 * 通常只给出定性信号而非清晰的定量评分 |
| **系统性人工研究**_由训练有素的评审员对代理输出进行结构化评分_ | * 来自多个人类评审者的黄金标准质量判断 * 处理主观或模糊的任务 * 为改进基于模型的评分器提供信号 | * 相对昂贵且周转慢 * 难以频繁运行 * 评审者间的不一致需要协调 * 复杂领域（法律、金融、医疗）需要人类专家进行研究 |

这些方法映射到代理开发的不同阶段。自动化评估在发布前和 CI/CD 中尤其有用，在每次代理更改和模型升级时作为质量问题的第一道防线运行。生产监控在发布后启动，检测分布漂移和未预料到的真实世界故障。A/B 测试在拥有足够流量后验证重大变更。用户反馈和记录审查是持续的做法，用于填补空白：持续分类反馈，每周抽样记录阅读，并根据需要深入分析。将系统性人工研究保留用于校准 LLM 评分器或评估以人工共识为参考标准的主观输出。

![Image 5](assets/005-image-5-99208f4cb7.png)

就像安全工程中的[瑞士奶酪模型](https://en.wikipedia.org/wiki/Swiss_cheese_model)一样，没有任何单一的评估层能捕获所有问题。多种方法组合使用时，穿过一层的问题会被另一层捕获。

最有效的团队组合使用这些方法：自动化评估用于快速迭代，生产监控获取真实数据，定期人工审查用于校准。

## 结论

没有评估的团队陷入被动循环——修复一个故障、引发另一个，无法区分真正的功能退化和噪音。及早投入评估的团队则发现相反的效果：开发加速了，因为故障变成了测试用例，测试用例防止了回归，指标取代了猜测。评估给了整个团队一个明确的攀登目标，将"代理感觉变差了"变成可操作的信息。其价值不断累积，但前提是你将评估视为核心组成部分而非事后补充。

模式因代理类型而异，但这里描述的基本原则是不变的。尽早开始，不要等待完美的套件。从你看到的故障中获取真实的任务。定义明确、健壮的成功标准。精心设计评分器并组合多种类型。确保问题对模型来说足够难。迭代评估以提高其信噪比。阅读记录！

AI 代理评估仍是一个初生且快速发展的领域。随着代理承担更长的任务、在多代理系统中协作、处理越来越主观的工作，我们需要不断调整技术。随着我们了解更多，我们将继续分享最佳实践。

## 附录：评估框架

几个开源和商业框架可以帮助团队无需从零构建基础设施即可实现代理评估。正确的选择取决于你的代理类型、现有技术栈，以及你需要离线评估、生产可观测性还是两者兼顾。

[Harbor](https://harborframework.com/) 专为在容器化环境中运行代理而设计，提供跨云提供商大规模运行试验的基础设施，以及定义任务和评分器的标准化格式。像 Terminal-Bench 2.0 这样的热门基准测试通过 Harbor 注册表发布，方便运行成熟的基准测试以及自定义评估套件。

[Braintrust](https://www.braintrust.dev/) 是一个将离线评估与生产可观测性和实验追踪相结合的平台——适合需要同时进行开发迭代和生产质量监控的团队。其 `autoevals` 库包含用于事实性、相关性等常见维度的预构建评分器。

[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供追踪、离线和在线评估以及数据集管理，与 LangChain 生态系统紧密集成。[Langfuse](https://langfuse.com/) 提供类似功能，作为满足数据驻留需求的团队的自托管开源替代方案。

[Arize](https://arize.com/) 提供 Phoenix，一个用于 LLM 追踪、调试以及离线或在线评估的开源平台，以及 AX，一个扩展 Phoenix 用于规模化、优化和监控的 SaaS 产品。

许多团队组合使用多种工具、构建自己的评估框架，或者仅使用简单的评估脚本作为起点。我们发现虽然框架可以成为加速进展和标准化的有价值的方式，但它们的好坏取决于你通过它们运行的评估任务。通常最好的做法是快速选择一个适合你工作流的框架，然后将精力投入到评估本身，迭代高质量的测试用例和评分器。
